# v0.2 pre-release audit

Full-app sweep for the v0.2 gate, run 2026-08-26 against `main` at the #158 merge. Read-only. I traced
each area against its intent doc and confirmed the runtime claims with real runs (the migration upgrade
path, the harness). No code was changed. This decides nothing; it's the board I triage the release from.

## Bottom line

Main is releasable as v0.2 on the code. No RELEASE-BLOCKER survived the audit in any hard boundary: the
turn lifecycle, the permission gate, containment, isolation, actor-gating, kill safety, and secrets are
all solid, several of them enforced twice over. Every Part A finding is FIX-IF-TIME or POST-RELEASE.

What blocks tagging v0.2 is release process, not code. The shortest list to cut it:

1. Bump the version. It's `0.1.0` everywhere and nothing bumps it.
2. Write the v0.2 release notes. The changelog's `[Unreleased]` is empty, and the delta since v0.1.0 is
   large (the whole rich-conversation arc, the projects tab, the security and isolation fixes).
3. Fix two stale KNOWN-ISSUES claims so the notes are honest: the Windows build is deterministically
   unsigned now, not "auto-signed with the machine cert", and the macOS Keychain caveat describes a
   model I already disproved.
4. Run the one owed manual gate: the in-app ASK click-through on a genuinely destructive command, on a
   packaged build. It's proven for approve/deny in a normal session, never against real risk end to end.

Do those four and v0.2 is cuttable. Nothing in the four is a code change beyond the version bump.

Two FIX-IF-TIME code items are worth a look before the tag if there's time, neither blocking: an
empty-final-text turn drops its Conversation entry on reopen, and task send-back runs in the wrong repo
if I rebind a colleague between the task landing in review and sending it back. Both are narrow.

## Part A: code / correctness / security

Ranked RELEASE-BLOCKER / FIX-IF-TIME / POST-RELEASE. None reached blocker.

### 1. Turn lifecycle + persistence — SOLID, no blocker

Verified line by line. Every side effect between `await runner.runTurn` and the final `setState(IDLE)`
is individually wrapped in `#safely` (live-close, bind-session, snapshot, record-reply, each record-tool)
and the idle reset is in a `finally`; `#safely` routes to `#report`, which is itself guarded so reporting
can't re-throw. `runner.runTurn` never throws (typed result). So once WORKING is set, IDLE is guaranteed.
`recordReply` writes the channel message first, then `persistTurnEvents` (fully self-guarded, can't throw),
so you can never get a `turn_events` row without its `channel_messages` row, and the 256 KB backstop drops
only the rich snapshot while the message is already saved. The `[turn] record-reply failed` path is
reachable only on a SQLite write failure, returns the colleague to idle, and keeps the session bound so the
next turn resumes. `runner-manager-resilience.test.ts` pins the intent.

- **FINDING 1a (FIX-IF-TIME): an empty-final-text turn drops its Conversation entry on reopen.**
  `runner-manager.ts` gates both `recordReply` and `persistTurnEvents` on `assistantText.trim() !== ''`.
  A completed or interrupted turn that made tool calls but produced no final text writes no
  `channel_messages` and no `turn_events` row (the tools still land in `activity_events`, so Activity keeps
  them). Live, the provisional bubble shows the work; on reopen the persisted re-read has nothing to render,
  so the turn vanishes from the Conversation tab. Narrow trigger (interrupted before the summary, or a turn
  ending on tool calls), real loss of the conversation entry. Fix: persist when text is empty but blocks
  exist.
- **FINDING 1b (FIX-IF-TIME): the opening `setState(WORKING)` is unguarded while the closing one is
  guarded.** `runner-manager.ts:322`. If `onStateChanged` throws after the WORKING write (a
  `webContents.send` on a webContents destroyed in a shutdown race), the throw escapes before the
  try/finally and IDLE is never written; the card reads Working until the next turn re-sets it. There's no
  boot reconciliation that clears a stale WORKING. Shutdown-race only, self-healing, but it's the exact
  class this file guards against. Fix: wrap line 322 in `#safely` too.
- **FINDING 1c (POST-RELEASE): `turnEventsFor` trusts the persisted block shape on read.** `index.ts`
  checks only `Array.isArray(blocks)` then casts, no per-block validation. A parseable-but-malformed
  snapshot (an `edit` block missing `hunks`) would reach the DiffViewer and could throw at render. We author
  these writes, so real risk is low; a shape-guard on read would match the function's own "one bad row never
  blanks history" promise.

### 2. Permission gate — SOLID, no blocker

Precedence is correct and iteration-order-independent: `resolvePermission` picks the most-specific match,
and breaks only a specificity tie with deny > ask > allow. A broad allow can't beat a specific deny. The
protected set (userData, ~/.ssh, ~/.aws, ~/.claude, git creds, the cloud stores) is enforced through the
same `resolveForCompare` case-fold and symlink resolution on both the scope and the request path, so the
2026-08-21 case bypass is closed and the DB file is unreadable to a colleague's tools. `confirm-on-loosen`
is a UI guard, which is correct since only I reach the rule-writing IPC.

- **FINDING 2a (FIX-IF-TIME, config-gated): the protected-path and secret-file denies don't cover MCP /
  `other`-category tools.** Those denies are authored on the `read` and `write` actions only. `toolCategory`
  maps every `mcp__*` tool (and anything unrecognized) to `other`, for which the gate extracts no path.
  Today `other` defaults to `ask`, so nothing is silently open. But the plan's own open question is whether
  to pre-allow a named MCP server to cut noise; the moment `other` is set to allow, an MCP filesystem or
  exec tool can read `~/.ssh/id_rsa` or write outside the repo with no protected-path deny in its way. This
  isn't the documented shell best-effort limitation; it's a distinct gap. Don't loosen `other` without
  extending the protected coverage into that category, and note it.
- **FINDING 2b (FIX-IF-TIME, documented-accepted): `read` is host-wide, not repo-scoped.** The default is
  `read: allow` with no repo-scoping rule, so a colleague can Read/Grep/Glob any non-protected file on the
  machine. The containment doc explicitly accepts this as an awareness leak, and writes stay repo-scoped, so
  the write boundary matches intent while the read default diverges from the plan's "on the project repo"
  wording. Flagging the doc/code divergence; the risk itself is the accepted read-leak.
- **FINDING 2c (POST-RELEASE, non-default): a deep custom `writePaths` can out-specify the secret-glob
  write-deny.** Specificity is segment-count-based and `**` counts as one segment, so a `writePaths` set 3+
  directories below the repo root with a `.env` inside it out-specifies the secret deny and the write is
  allowed (read is still denied). Never happens at the default `writePaths` (null → repoRoot); config-
  dependent and bounded.

### 3. Containment (#144) — SOLID, no blocker

`hitsSelf` guards create, update, both `resolveTarget` implementations (chat and task), and the task-diff
read. A hand-edited DB row with a self-path still can't spawn, because the spawn-time guard refuses it
regardless of what was stored, which is the security-critical half the containment doc names. Rebind
doesn't re-validate the target, but it only sets `activeProjectId` and the spawn guard catches a bad
target, so the defense in depth holds. `staffordSelfPaths` reads `process.cwd()`, which in a packaged
launch can be broad, but the effect is only ever over-refusal, never under-refusal.

### 4. Isolation (#61 / claudeMdExcludes / --setting-sources user) — SOLID, no blocker

Chat and task turns share one `#runTurn`, which seeds the managed config and sets `CLAUDE_CONFIG_DIR` on
every turn. `--setting-sources user` is in `HEADLESS_ARGS`, so a repo's `.claude/settings.json` and
`settings.local.json` are dropped while the managed user settings (carrying `claudeMdExcludes`) are kept.
A repo can no longer inject settings or hooks or leak `additionalDirectories`. The old owed item, that a
colleague writing `.claude/settings.local.json` could influence its own next session, is closed by this:
the colleague no longer reads project or local settings at all.

### 5. Actor-gating — SOLID, no blocker

The boundary is structural: a colleague is a stream-json subprocess with no preload, no contextBridge, no
ipcRenderer, so no IPC channel is reachable to it. Every write channel added since v0.1.0
(`project:update/delete`, `colleague:rebind`, `question:answer`, `permissions:*`, `approval:answer`,
`tasks:*`, `channel:reply`) is renderer-to-main only, registered once with a shape guard, none an event
channel. No channel lets a caller name the actor it acts as; the task service hardcodes the actor at every
write, pinned by the `handlers.test.ts` regression that a smuggled `actor` key rides along unread. A
colleague can never reach task-done: `canTransition` refuses `colleague → done` unconditionally, and the
completion sentinel maps to needs-you for my review, never to done. `question:answer` resolves exactly the
pending ask by id and a colleague can't reach the handler.

### 6. Kill safety — SOLID, no blocker

Kill is by exact spawned pid or own process group only, never by image name. POSIX: `killTree` kills the
process groups in a snapshot rooted at the child pid, refuses any group containing Stafford, and sweeps
survivors by exact pid, skipping self. Windows: `taskkill /PID <pid> /T /F`, no `/IM` anywhere, pinned by
`platform.test.ts`. The caller passes the exact spawned `child.pid`. The one residual is the snapshot-to-
kill race named in the module header, inherent and narrowed, POST-RELEASE at most.

### 7. Rich-conversation arc (phases 1-7 + reasoning nesting + AskUserQuestion + collapse) — SOLID, no blocker

`live-turn.ts` `apply` degrades on every unknown event and block type, every `JSON.parse` is wrapped, and a
consumer throw in the stream handler is swallowed so the stream still reaches its result. `groupTurn`
handles multi-thinking-span, answer-then-more-thinking, all-thinking, empty blocks, and redacted-thinking-
no-actions, all directly tested, with no throw path. AskUserQuestion answers route by unique pending id to
one colleague and one tool call; missing id is a no-op. The DiffViewer preview is safe for blocks the
builder produces.

- **FINDING 7a (POST-RELEASE, theoretical): the renderer picks which ask form to show by `toolUseId`
  matched globally, not scoped to hireId.** CLI tool_use ids are globally unique, so it's safe in practice;
  the only collision vector is two colleagues each with an empty-string id pending ask, which can't happen
  because `can_use_tool` always carries a tool_use_id. A defensive fix would scope the lookup by hireId too.

### 8. Projects tab + rebind (#158) — SOLID, no blocker

Rebind is a clean fresh session: it sets the new `activeProjectId`, clears that project's session slot (so
the next turn resolves a null resume id and Claude starts fresh), and moves `activeSince` to now, so the
conversation, activity, and turn views read clean from the new binding. A parked colleague can't be
spawned by any path (both `resolveTarget` return null, and task assign/start/send-back throw). The write-
reply contract is honored on save, remove, and rebind.

- **FINDING 8a (FIX-IF-TIME): task send-back resolves cwd by the colleague's current binding, not the
  task's project.** `#sendBack` calls `resolveTarget(task.agentId)`, which reads the hire's current
  `activeProjectId`, while resuming the task's original session and reusing the task's original baseline
  tree. Scenario, all my own actions: assign a task in project A, it lands needs-you, I rebind the colleague
  A to B (allowed while idle), then I send the old task back instead of failing it. The send-back runs in
  B's working directory, resuming A's session, diffing against A's baseline. A task branch built in the
  wrong repo from the wrong baseline. Not a colleague exploit and not a boundary breach, but a real cross-
  project correctness bug from the rebind-times-tasks interaction. Narrow. Fix: send-back should resolve cwd
  and baseline from the task's own project, or refuse a send-back when the colleague was rebound off the
  task's project.
- **FINDING 8b (POST-RELEASE): project delete leaves orphaned rows in tasks, permission_rules, and
  channel_messages.** `deleteById` is a bare DELETE and no table declares an FK to projects, so nothing
  cascades; delete only drops the session slot. Harmless for security (project ids are UUIDs, so a recreated
  project can never re-associate, and orphaned messages are filtered out of per-hire views by `activeSince`)
  and a data-hygiene gap plus a doc overstatement, since `project-manage.ts` claims no dangling reference is
  left. Fix: also call `permissionRules.deleteForProject(id)` on delete, or soften the claim.

### 9. Secrets — CLEAN, no blocker

Full git-history scan for private keys, cloud keys, and provider tokens returned nothing. `.env` never
appears in history and is correctly gitignored; only `.env.example` is tracked, and it documents only the
non-secret `STAFFORD_*` dev knobs with no real values. The credential is never logged: the seed result
carries only booleans and a mode, and the macOS credential read discards its failure reason on purpose. No
personal identifiers in tracked files. One stale reference: `.env.example` mentions a token at
`~/.agent-dashboard/token` that nothing in the code reads; harmless, worth trimming.

### 10. Dependencies — HEALTHY, no blocker

Every `dependencies` and `devDependencies` entry is an exact version, no `^`/`~` ranges. The lockfile is
committed and consistent. `npm audit --omit=dev` reports 0 vulnerabilities. The electron-builder devDep
debt is resolved (bumped to 26.15.7, pinned exact).

### 11. Cross-platform

The platform abstraction is genuinely clean: no raw `process.platform` branching in feature code, every OS
difference behind one injected interface, so darwin and linux logic is exercised by the Windows suite.
Nothing in the platform layer crashes on mac or linux; the one Windows-only env read degrades to a safe
default. Ledger for the notes:

- Windows-only, verified: Git Bash discovery, `taskkill` tree kill, `icacls` owner-only ACL, ConPTY resize,
  the USERNAME/USERDOMAIN ACL account.
- Cross-platform, tested from Windows: path normalisation and equality, the claude locator, kill-tree
  ordering, process-tree parsing.
- POSIX-shared, macOS-measured, Linux-never-run: the group-kill plan, the `ps` process table, detached
  spawn.
- macOS structured-but-partly-unverified: the Keychain credential read (see below).
- Packaging: Windows zip/x64 unsigned is a real CI distributable; macOS dir/arm64+x64 is compile-proof only;
  no Linux target.

- **FINDING 11a (FIX-IF-TIME, notes honesty): the KNOWN-ISSUES "auto-signed with the machine cert" section
  is stale and wrong.** The Windows build is deterministically unsigned now: `electron-builder.yml` points
  `signtoolOptions.sign` at a no-op hook, and `check-packaged-bundle.cjs` fails the build if the exe carries
  any Authenticode signature. The employer-cert-leak that section warns about is already closed in code.
  Rewrite it to "ships unsigned, SmartScreen warns, verified in CI" for the release.
- **FINDING 11b (POST-RELEASE, macOS-only): the Keychain credential path has unverified guesses and a second
  stale doc.** The service name (`Claude Code-credentials`, unsuffixed) and the account (`os.userInfo()
  .username`) are guesses; a wrong one fails silently as "Not logged in", it doesn't crash. And the
  KNOWN-ISSUES macOS caveat still says the managed dir authenticates through Keychain with no copy, which I
  already measured false (Claude Code with `CLAUDE_CONFIG_DIR` set doesn't consult Keychain, so the seed
  reads Keychain and writes a 0600 file, a deliberate, disclosed protection downgrade). Out of the Windows
  path; fix before any macOS ship.
- **FINDING 11c (POST-RELEASE): `assertSupported` is never wired into boot.** The linux platform is marked
  `supported: false` with a comment saying the app refuses to start there, but nothing in the boot path
  calls `assertSupported` or reads `.supported`, so on Linux the app proceeds against untested code. A truly
  fourth platform does throw. No Linux build is produced, so low impact, but the "refuses to start" claim is
  currently untrue.

### Draft v0.2 release-notes delta (real, from the git log since v0.1.0)

- Rich conversation: a colleague's turn streams live and re-renders on reopen, with markdown replies,
  tool-call islands, shell output and file reads, inline edit diffs, a thinking island, a live TodoWrite
  checklist, in-reasoning actions nested in a collapsed reasoning block, and action bodies collapsed to a
  short preview by default. The Transcript tab retired; Activity enriched with expandable action bodies.
- AskUserQuestion: a colleague's clarifying question renders in the conversation with clickable choices and
  a free-text option, and the answer routes back to unblock the turn.
- Projects tab: full project management (view, edit the folder with the same validation as create, delete)
  plus parking and rebinding colleagues, a rebind being a clean fresh session.
- Security and isolation: the permission gate now enforces the same credential directories the config
  screen shows as protected (#125); a colleague can't be pointed at Stafford's own directory (#144); a
  repo's own settings and other-directory awareness no longer leak into a colleague session (#157).
- Reliability: a turn's reply and actions no longer vanish silently on a write failure, and the colleague
  always returns to a usable state (#155).
- Notifications: an OS notification when the needs-you count rises.

## Final bottom line

Main is releasable as v0.2 on the code, with no blocker in any hard boundary. The gate to actually tag it
is four release-process steps: bump the version, write the notes, fix the two stale KNOWN-ISSUES claims,
and run the owed packaged-build ASK-on-a-destructive-command check. Optionally fix the two FIX-IF-TIME code
items (empty-final-text turn, task send-back wrong-repo) if there's time; neither blocks.
